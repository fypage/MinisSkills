# 案例：同一容器、两种章节结构 —— 调试脚本为何没试出来

- 时间：2026-10-16
- 站点：`m.bookmaopu.com`（猫扑中文）
- 触发：真机反馈「正文没有分段、挤成一坨」+ 贴出正文原文
- 层面：规则层（书源取值）+ 工具层（调试脚本）
- 结论层级：`RULE_SAMPLE_OK`（两本对照实测；真机未复验）

---

## 一、现象与初始误判

用户贴出 `/12377/40994137/` 的正文，特征有二：

1. **整章挤成一坨，几乎无分段**；
2. 正文里混有站方声明「报送后维护人员会在两分钟内校正章节内容,请耐心等待。」，并在分页处**硬断**。

初始方向（**错的**）：先怀疑客户端排版设置、再怀疑客户端缓存旧规则。
缓存判断**是对的但不是根因**——即便换上新规则，问题依旧，因为**规则本身写窄了**。

---

## 二、根因：同一 `#nr1`，两本书结构不同

用同一站点两本书对照取样：

| 书 | URL | `#nr1` 内部 |
|---|---|---|
| 《她是剑修》 | `/3375/2376896/` | **33 个 `<p>`**，一句一段 |
| 《食仙主》 | `/12377/40994137/` | **43 个 `<br>` + 1 个空 `<p>`**，整章一坨 |

**同一容器、两种结构并存。**

于是：

- `#nr1 p@text` / `#nr1 p@textNodes` 在 `<p>` 型书上正常，
  **在 `<br>` 型书上取到空 / 只剩空白** → 用户看到的「没分段、一坨」。
- 书本成品与截图里的脏句（站方声明）来自**旧规则 `#nr1@text`**（取整容器文本会把
  `#nr1` 末尾的报错块一并吃进）。

**站方声明实际位置**（`/12377/40994137/2.html`，**在 `#nr1` 内部末尾**）：

```html
<div id="center_tip"><b></b></div>
<div align="center">
    <a href="javascript:postError(45513907,113918);" …></a>,
    报送后维护人员会在两分钟内校正章节内容,请耐心等待。
</div>
```

---

## 三、正解

```jsonc
"content": "#nr1@text",          // 通吃 <p> 型与 <br> 型；@text 会把 <br> 转成换行
"replaceRegex": "阅读提示：.*?正常阅读！\n?\n?|,?\\s*报送后维护人员会在.{0,8}校正章节内容,?请耐心等待。"
```

要点：

1. **不要用 `p@text` / `p@textNodes` 绑定 `<p>`**——同站不同书（甚至同书不同章）结构会变。
   容器级 `@text` 才是通吃写法（`<br>` 由 `@text` 转换行）。
2. **净化不得锚 `^`**——「阅读提示」在**每一分页**各出现一次，锚行首只能清掉第一份。
3. 净化须同时覆盖**站方报错块**（它虽在 `#nr1` 内，但结构上不属于正文）。

实测（链式取全文）：

| 书 | 页 | 行 | 字 | 脏检查 |
|---|---|---|---|---|
| 《食仙主》`/12377/` | 2 | 38 | 2110 | 全 False |
| 《她是剑修》`/3375/` | 3 | 38 | 2800 | 全 False |

## 四、★核心：调试脚本为什么没试出来

**两个盲区叠加，互相掩护。**

### 盲区一：样本单一 —— 只验了 `<p>` 型

所有验证都落在 `<p>` 型那本上，于是：

- 先验 `p@text` → 取到 1221 字，**看着正常**；
- 再验 `p@textNodes` → 取到 1221 字，**也正常**。

两次都对，因为**两次验的都是本来就通过的那本**。
真正会失败的 `<br>` 型章节，**一次都没进过测试集**。

> 这叫**拿必然通过的样本，去证必然通过的结论**。
> 样本选择错误，比断言写错更隐蔽——断言错会报错，样本错只会一路绿。

### 盲区二：`textNodes` 静默降级 —— 我改的规则从未被真正执行

`debug_source.py` 的 `VALUE_TAILS` 白名单**缺 `textNodes`**，落到：

```python
if attr not in VALUE_TAILS and attr != 'text':
    attr = 'text'          # ← 静默降级
```

于是「`textNodes` 验证通过」实际是**降级成 `text` 之后的结果**：

- 我改的这条规则，**在脚本里从未被执行过**；
- 但脚本**照样报「通过」**。

> 若脚本当初报「`textNodes` 不支持」，我至少会去看它是什么、该不该用。
> **静默降级把「不支持」伪装成「已支持」**，是假绿的头号来源。

### 两者的关系

| | 作用 | 后果 |
|---|---|---|
| 盲区一 | 让我**问错问题** | 拿 A 书去验 B 写法 |
| 盲区二 | 让我**拿到假答案** | 降级后仍报通过 |

**两次「绿」，一次比一次更远离真相。**

## 六、本案例修掉的工具缺陷

| # | 症状 | 真因 |
|---|---|---|
| 1 | `#nr1 p@text`（38 个 `<p>`）只返第 1 个 → 误报「取值 15 字」 | 多元素 `@text` 只取 `vals[0]`；真机语义是**全部拼接** |
| 2 | 「`textNodes` 验证通过」为假 | 白名单缺项 → 第 297 行静默改成 `text` |
| 3 | `@css` 里的 `textNodes` / `ownText` 不被放行 | `css()` 只放行 `text` |

修后：`textNodes` 实现真机语义（取元素下全部文本节点、含 `<br>` 转出的换行、逐节点拼接）；
`ast.parse` + 64 项解析器回归全 PASS。

**另记**：`exec_js_rule_node.py` 对相当一部分 `@js` **一律返回空串**
（连 `@js:result='HELLO';` 都返空）→ **不可作裁定依据**，改以 `node` 直跑等价 JS 验证。

## 七、可复用清单

- [ ] 验正文取值时，**同时**准备 `<p>` 型与 `<br>` 型两个样本。
- [ ] 断言看**行数 + 首段 + 末段 + 脏词**，不看单一「长度」。
- [ ] 净化正则**不锚 `^`**（分页页各一份）。
- [ ] 站方声明可能就在正文容器**内部**，须显式剔除。
- [ ] 调试工具对**未支持的后缀必须报错**，不得静默降级。
- [ ] 定位问题的第一手证据来自**目标站点原始输出**，不是自造样本。
